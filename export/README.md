# Machine-readable export

Generated by `scripts/export_db.py` from the Markdown and YAML in this repo (daily by the
GitHub Action, or by hand). Do not edit these files; edit the sources and re-run the script.
The output is deterministic: an unchanged repo gives byte-identical files.

| file | what |
|---|---|
| `aggregat.sqlite` | one SQLite file, queryable with `sqlite3` or any SQLite library |
| `aggregat.json` | the same tables as JSON arrays, for tools without SQLite |

## Tables

| table | from | columns |
|---|---|---|
| `meta` | - | `checked` (date of the last update check), `counts`, `research_snapshot` (id of the current research state, as in research/AGGREGAT_RESEARCH.md) |
| `devices` | `data/devices.yml` | slug, name, family, phase |
| `projects` | `data/projects.yml`, `state/repo_meta.json` | id, name, author, kind, list, own_mods (JSON list, see the next table), devices, repo, license, status, base_os, version, last_activity, tested, tested_note (mods: unit / partly / emulator / not-stated, as the authors claim), notes, links, sources; from GitHub (`scripts/repo_meta.py`, refreshed daily): owner, created, pushed, stars, forks, language, gh_fork, gh_license (GitHub's licence detection, used only when `license` is empty) |
| `relations` | `relations:` in projects.yml | project, type, target, evidence |
| `own_mods` | `own_mods:` in projects.yml | platform (project id), name, author, devices, version, path, tested, note, origin, what: mods a loader or platform ships itself, without an entry of their own |
| `rules` | `hardware/AGENT-RULES.md` | id (A1, B7...), section, title, text, evidence, sources, devices |
| `sources` | `hardware/SOURCES.md` | key, what, url |
| `conflicts` | `hardware/CONFLICTS.md` | id (O1.., S1..), status, topic, a, b, details, devices |
| `incidents` | `hardware/INCIDENTS.md` | id (I1..), group (stock, mod, emulator-or-tool, recovery-or-link), title, unit, seen, cause, cause_found_by, fix, status, evidence, sources, rules, fact_file, devices |
| `stock_bugs` | `hardware/STOCK-BUGS.md` | id (SB1..), title, device_os, area, symptom, trigger, cause, workaround, test_tip, found_by, status, evidence, sources, incidents, devices |
| `incident_rules` | `hardware/INCIDENTS.md` | incident, rule: which rule each incident taught or confirmed (join with `rules`) |
| `facts` | `hardware/devices/*.md`, `hardware/common/*.md` | id, file, line, section, text, evidence, sources, devices, addresses |
| `facts_fts` | FTS5 index over `facts` | text, section, devices |
| `goals` | goals table in `RESEARCH-MAP.md` | id (G1..), goal, status, moved_by |
| `tasks` | shared to-do in `RESEARCH-MAP.md` | id (T1..), task, devices, needs, effort, value, status (open/done) |
| `hypotheses` | `hardware/HYPOTHESES.md` | id (H1..), goals, inference, derived_from, devices, test, kind (stock/probe/build), status |
| `research_links` | goal columns of both | item (T/H id), goal, via |
| `participants` | `research/PARTICIPANTS.md` | project, repo |

A fact is one top-level bullet (with its continuation lines). `evidence` is the tag in the
bullet (`hw`, `emu`, `doc`, `?`); without one, the tag in the section's lead paragraph, its
heading or the file's intro; empty if none of these has one (mostly rules, open questions and
pointers). `sources` are the `{keys}` in the bullet, its headings and the section's lead
paragraph, else the keys named in the file's intro. List columns (devices, sources, addresses) are
JSON arrays in text form. `file:line` points back to the Markdown, which stays the place to edit.

## Example queries

```sh
# Everything known about the Digitone II reverb, best evidence first
sqlite3 export/aggregat.sqlite "SELECT file, line, evidence, text FROM facts
  WHERE id IN (SELECT rowid FROM facts_fts WHERE facts_fts MATCH 'reverb')
  AND devices LIKE '%digitone-2%' ORDER BY evidence='hw' DESC"

# Which facts mention an address
sqlite3 export/aggregat.sqlite "SELECT file, line FROM facts WHERE addresses LIKE '%0x40000400%'"

# Open conflicts for the Digitakt II
sqlite3 export/aggregat.sqlite "SELECT id, topic FROM conflicts WHERE status='open' AND devices LIKE '%digitakt-2%'"

# What went wrong on Digitone II units, and the rules it taught
sqlite3 export/aggregat.sqlite "SELECT i.id, i.title, r.id, r.title FROM incidents i JOIN incident_rules ir ON ir.incident=i.id JOIN rules r ON r.id=ir.rule WHERE i.devices LIKE '%digitone-2%'"

# Forks and copies of a project
sqlite3 export/aggregat.sqlite "SELECT project, type, evidence FROM relations WHERE target='overtone'"

# Tests a stock unit can run, with the goal each one moves
sqlite3 export/aggregat.sqlite "SELECT h.id, h.devices, h.test, group_concat(l.goal) FROM hypotheses h
  JOIN research_links l ON l.item = h.id WHERE h.kind = 'stock' GROUP BY h.id"

# Everything that moves one goal
sqlite3 export/aggregat.sqlite "SELECT item FROM research_links WHERE goal = 'G8'"

# Rules that only rest on documentation
sqlite3 export/aggregat.sqlite "SELECT id, title FROM rules WHERE evidence NOT LIKE '%hw%'"
```

## Duplicate report

`scripts/find_duplicates.py` reads the database and writes
[`hardware/DUPLICATES.md`](../hardware/DUPLICATES.md): pairs of facts in different files
that say much the same (shared words, or two shared addresses). Use it when consolidating:
keep the fact in the file where it belongs and link to it from the other, unless the second
is an independent confirmation (then keep it as a second source).
