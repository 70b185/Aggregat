## From the official manual (OS 1.12; first part only - the MIDI appendix C was not reachable)
- 16 tracks, each audio (SYN machine) or MIDI; **16 audio voices** (one per track) each with SYN machine, bit reduction, filter, amp and LFO; 12 V DC via PSU-3c; balanced/unbalanced 1/4" I/O, inputs also over USB; MIDI IN, OUT/SYNC A, THRU/SYNC B (SYNC outputs can send DIN sync); USB type B, class compliant, audio + MIDI, Overbridge. Wait at least 30 s after power-off before powering on again; ambient max 40 deg C. `[doc]` {dn2-manual}
- **Data model:** +Drive holds up to 128 projects and a library of 2,048 presets; a project = 128 patterns (8 banks x 16), 16 songs, a 128-preset pool and general settings; a pattern holds up to 16 presets (one per track), sequencer data, TRIG page settings, BPM, length, swing, time signature, MIDI track parameters; a preset holds SYN1, SYN2, FLTR, AMP and LFO pages. Digitone I projects can be imported but patterns may differ - re-save on Digitone II before exporting. `[doc]` {dn2-manual}
- **MIDI in:** notes 0-15 trigger tracks 1-16 (default channels), notes 16-84 (E2-C7) play the active track chromatically (C5 = 60 is middle C), program change 0-127 selects patterns A01-H16, tap tempo by note C0 on the FX CONTROL channel; MIDI tracks: up to 16 notes per step, pitch bend, aftertouch, 16 assignable CCs (CC1-8 on the FLTR page, 9-16 on AMP); the lowest-numbered track wins when tracks share a channel. TRIG modes: TRACKS, VELOCITIES (TRIG 1-15 = velocity 8..120 in steps of 8, TRIG 16 = 127), RETRIGS (1/1 ... 1/64). `[doc]` {dn2-manual}
- Appendix C groups (numbers not extracted): C.1 Track, C.2 Trig, C.3 Source, C.4 Filter, C.5 Amp, C.6 Euclidean, C.7 FX, C.8 MOD, C.9 Send FX, C.10 Mixer, C.11 VAL, C.12 MISC. Startup menu entries: TEST MODE, EMPTY RESET, FACTORY RESET, OS UPGRADE, EXIT (other sources: TRIG 4 = OS UPGRADE). `[doc]` {dn2-manual}

## Architecture
- ColdFire main CPU (big-endian code, GCC-built, C++ RTTI names remain); SHARC+ audio DSP. `[doc]` {dn2-cfw} {dn2-firmware-explore}
- `MAIN OS` section: 3,085,696 bytes on 1.10E and 3,192,192 bytes on 1.11 (unpacked), loads at `0x40000400`. `[doc]` {dn2-firmware-explore}
- Container **signed with HMAC-SHA256** with a key derived from the image itself, so the tools re-sign modified images ([`../common/firmware-container.md`](../common/firmware-container.md)). `[doc]` {dn2-firmware-explore}
- **The OS keeps its C++ RTTI, enough to name most code:** on 1.12, 12,350 functions and 1,624 types (752 classes, 872 lambdas), 741 with vtables; about a third of all instructions sit in a function that RTTI names. A function that loads a vtable is a constructor or destructor; a `std::function` lambda's typeinfo names its enclosing method with the signature. The DSP has no application RTTI. `[doc]` {dn2-skill-firmware}
- **1.11 to 1.12:** sections 2, 4, 7 and 8 are byte-identical (the DSP did not change); section 3 is relinked (+4 KB, BSS +0x1000, DMA alias +0x8000). Overtone ships on 1.12 by translating every 1.11 patch address through a code map built from anchors of 10 matching instructions. `[doc]` {dn2-skill-firmware}
- **Cache map (OS 1.11 and 1.12):** the bootstrap leaves the data cache off (CACR `0x000cc100`), but the main OS start-up at `0x40000554` writes CACR `0xa50ce100` and ACR0 `0x4007e020`: `0x40000000-0x47ffffff` is cached copyback, everything else uncached, including the SSI DMA buffers at `0x4e6e7100`. Reading those buffers byte by byte from a mod is slow enough to stall the sequencer: Digiwerk's first multichannel USB build (UM01) packed the SSI slots with byte-wise uncached reads and lagged until unusable; reading each of the 14 slots once as a 32-bit word (UM02) ran on the unit with busy sequences and no lag. Checking only the bootstrap's CACR gave a wrong "cache off" conclusion first, corrected the same day. `[hw]` {dn2-cfw-handoff} {dn2-cfw-usb} ([I10](../INCIDENTS.md#i10-byte-wise-reads-of-uncached-dma-buffers-stalled-the-sequencer))
- DSP works per block; the stock handler can be interpreted offline (sharcvm); new effects are portable C, compiled with selache/selcc and spliced into the DSP section. `[doc]` {dn2-cfw}

- **Board PCBA0109B, read from photographs of the parts** (dnfw `docs/hardware.md`, 2026-09-12) {dn2-hw}. The same board number as the Digitakt II is reported.
  - CPU: ColdFire **MCF5441SCMJ250** (MCF5441x, 250 MHz). Not the V4e that older notes inherited from the Octatrack.
  - RAM: NANYA NT5TU128M8HE-AC, 128 MB DDR2.
  - Flash: **Winbond W25Q128JV** (16 MB SPI NOR, by the ColdFire).
  - Storage: Kingston EMMC32G-TX29 (32 GB eMMC).
  - DSP: **ADSP-21569** (KBCZ10) with its own Kingston DDR3 beside it.
  - Codec: **AKM AK4621EF**, 20 MHz crystal by the SHARC.
  - There is no flash chip by the DSP: the ColdFire boots the SHARC (section 7 is its boot stream). `[hw]` (photos)
- **Flash-part mismatch worth knowing:** the bootstrap's DYB sector protection (`0xE1`) is applied only on a Spansion S25FL (`0x01 2018`), and digikit's DT2 reading names that part. **On a unit with the Winbond part, that lock has no effect** (Digiwerk T1.5/T1.4). Do not count on hardware write protection of the bootstrap. `[?]` {dn2-hw} {dn2-cfw-t15}
- Third-party claim about the family (not measured):
  - Digitone mk1: two MCF54415 plus a Spartan XC3S50A.
  - Digitakt mk1: one MCF54415.
  - Digitakt II: one MCF54415-class part plus the ADSP-21569.
  - Syntakt: two MCF54415, XC3S50A and XC3S200A (the latter driving the analog side).

  digikit's Syntakt 1.42 reading (an FPGA section, a second ColdFire program) fits. `[?]` {dn2-hw}

- **Cross-device transplant (armio's R012, DN2 1.11):** the Digitakt II 1.16 sample machines and their UI (ONESHOT, WERP, STRETCH, REPITCH, GRID, SLICE, stereo samples, sample browsing) run on a Digitone II. Donor routines are extracted from the official DT2 file and relocated at build time. `[doc]` {armio-r012}
  - The same build makes **USB AUDIO class-compliant with 42 capture channels** (48 kHz/24 bit, 21 stereo pairs) and a stereo return. Digiwerk's USB01 note sketched this. `[doc]` {armio-r012}
  - **R013 (2026-11-05) adds the missing sample-storage setup:** SYSTEM > FORMAT SAMPLES creates a sample filesystem in an area the stock OS does not expose as sample storage, and erases that area (including other mods' data there). Formatting, restart, Transfer capacity (about **20 GB** on the tested DN2) and uploads afterwards passed on the unit. `[hw]` {armio-samples}
- **Two independent 42-channel USB audio builds now exist for the DN2**, on different OS versions: armio's (1.11, above) and Digiwerk 0.3.0 (1.12, USB MULTI/MIDI as a fourth USB CONFIG choice; UAC 2.0, 48 kHz/24 bit; inputs 1-32 the 16 tracks, 33-34 main, 35-40 delay/reverb/chorus returns, 41-42 the inputs; used with a Mac and with AUM on an iPhone). Digiwerk's USB addition changes only the main OS, leaving each build's DSP section unchanged. `[hw]` {dn2-cfw-030} {dn2-cfw-usb}
  - **Historical size estimate (UM03):** the USB addition's code and BSS added about 2.6 KB to the existing 1 MB mod region. `0x47e00000-0x47e075a4` describes the combined used span, not the USB addition alone; this is not a size measurement of the later UM04 implementation shipped in 0.3.0. `[doc]` {dn2-cfw-um03}
  - **Recorder** adds recording/resampling, source selection, normalization, trimming, audition, saving to +Drive and optional track assignment. VOICE cycles Voice Setup, Sample Manager and Recorder. Exact trimmed-file comparison and full Recorder-source coverage remain unverified. `[doc]` {armio-recorder}
  - **R012 requires only the two official OS files.** Native and browser builds verify the final SHA-256; the browser builds locally without uploads. No sample bank or factory library is required; historical exact T1E2/R003/R008/R011 builds still need their original private bank. `[doc]` {armio-r012} {armio-browser}
  - R012 stable is owner-confirmed for stock audio, samples, Recorder and USB audio, including after project changes. This is not exhaustive workflow or endurance validation. `[hw]` {armio-r012}
- **USB audio repeating old audio after a project change (armio, R007-R011; fixed 2026-11-03):** USB audio froze or repeated while headphones and UI kept working; accepted publications stopped, rejected ones rose by 16,392 in about 10.9 s, and USB transfers kept running. Cause: the render-time TX selector follows RX completion and is not a TX ownership grant, but the build had bound the retained queue head to a destination derived from that older phase. R011 picks the candidate from the current DMA START and leaves the ownership guards to decide; the owner confirmed playback after project changes, and R012 is the stable build. Endurance and end-to-end USB latency are unmeasured. `[hw]` {armio-usb} {armio-r011} ([I13](../INCIDENTS.md#i13-usb-audio-repeated-old-audio-after-a-project-change))

## Sampler port lifecycle findings (DN2 OS 1.11, 2026-11-06)

- **Incremental working-state updates are a separate persistence path from whole-project saves.** In armio's port, sample load/unload updates a separate identity companion and sends the native ProjectSettings notification. Its queued worker `0x400469E2` calls settings serializer `0x400DF57A` at `0x400469FE`; it does not pass through whole-project serializer `0x400E1494`. The extension had been attached only to the latter, so the native settings mirror advanced while the added sample mirror stayed stale. The alternating boot snapshots at sectors `0x40000` / `0x48000` are separate from explicitly saved project slots (see the existing [storage map](../common/memory-maps.md)). R020 replay reproduced a new identity absent from the prepared backup and from a fresh emulated boot. R022 updates the working companion at the narrow settings-worker callsite under the existing project mutex, checking destination, owner, readiness and matching UIDs; explicit saved companions remain untouched. Unchanged identities skip the 16 KiB copy/CRC. Load, unload, fresh-boot restore and failure guards passed native replay; physical shutdown and freeze recovery are unverified. These extension defects are not evidence of a stock DN2 autosave bug. `[emu]` {armio-r022} ([I52](../INCIDENTS.md#i52-new-project-samples-were-missing-after-reboot))
- **A Machine change can leave a port's old SYN view attached even when the Sound has changed.** Native selection reselects the view when audio/MIDI classification changes; stock synth to a ported sampler remains an audio track. Generic Project, ActiveTrack and Sound notifications redraw but do not replace the view. R020 replay reproduced knob D reaching the stock handler after switching to all six samplers. R021, included in R022, reconciles the exposed SYN view through the existing factory and native selector on the next UI poll, deferring during modal ownership, selected-trig edits, construction and expired ownership. Ten transitions and nine guards passed. Earlier tests explicitly selected SYN before turning D and therefore repaired the state they were meant to test. Hardware confirmation is pending. `[emu]` {armio-r022} ([I51](../INCIDENTS.md#i51-the-sample-popup-did-not-open-after-switching-machines))

## Parameter table
- 1.12: one OS table of **321 rows**, no free space after it. dn2-cfw's patch GT00 copies it at start-up into free memory with room for **384 rows**; GT01 adds 17 hidden rows (3-band compressor). `[hw]` {dn2-cfw}
- **Projects store values by slot, not by row**, so moving the table keeps the saved format; new rows follow `docs/parameter-table-growth.md` (not read yet). Table growth was first done on 1.11 for the LFO4 mod in dn2_firmware_explore. `[doc]` {dn2-cfw}
- Overtone: LFO 3's storage holds ARP 2, so a sound that used LFO 3 loses it; ENV3/LFO3 no longer exist in Overtone. `[doc]` {overtone}

### Parameter table details (OS 1.12; dn2-cfw `docs/parameter-table-growth.md`)
- Each parameter is one **60-byte row**. Table base `0x401f83a4`, stock 321 rows. Offsets: `+0x00` group (set/page family), `+0x04` k (the slot that holds the value in its set), `+0x08..0x14` min/max/default/bipolar, `+0x18` MIDI CC, `+0x1c` NRPN, `+0x20` Overbridge id, `+0x28..0x38` names/formatter/suffix. A separate RAM display table holds glyph, lock flags and randomiser data. `[doc]` {dn2-cfw-param-table}
- Row ids are **not saved**; projects store values by slot k through fixed k-to-stored-id tables. Slot maps and CC/NRPN maps are rebuilt from the table at each boot (`0x400dc634`); page records are built at boot from code constants (`0x400c2c4e`). Moving the table does not change project storage; **new rows do**, via their k and display flags. `[doc]` {dn2-cfw-param-table}
- Grown table at `0x47D00000`, room for 384 rows (`0x180`), copied at boot by `pg_boot` (called from `0x40000568`). New row ids `0x141`-`0x17f` (63 ids); the same-length-edit ceiling is `0x1e0` (480 rows). 56 address operands in 53 functions had to be redirected; 57 row-count compares changed (`#0x141`->`#0x180`, `#0x140`->`#0x17f`; five look similar and stay). The display-table reader at `0x400c257c` has its first 10 bytes turned into a jump plus two nops. The MIDI input cache (33 constants in five functions) grows by 12,852 bytes. `[doc]` {dn2-cfw-param-table}
- **The grown table ran on a unit** (Digiwerk GT00/GT01, OS 1.12, 2026-10-13): boot, cold start, +Drive project save and load were all reported fine, and GT01 added 17 hidden rows for the 3-band compressor that later shipped (CMP3). In the emulator, not one instruction read the stock table after the boot copy. Since projects store values by slot k, and stock saves FX k 25-69 only, values in new slots k 70+ need their own storage (the 3-band compressor uses 28 FX-record words that stock never writes or reads). Whether such a project opens cleanly on a stock OS has not been reported. `[hw]` {dn2-cfw-t65}
- New rows carry Overbridge ids of `0x400` and up. Each is sent to the plugin as soon as its value changes; what the plugin does with an id it doesn't know is not known. `[emu]` {dn2-cfw-t65}
- Map builders hold 101 entries each, so k must stay in range (0..100 for sound/FX/MIDI, 0..25 for trig). Stock saves FX k 25-69 only; FX k 70+ and sound k 65 and 100 are **not saved**. `[doc]` {dn2-cfw-param-table}
- Rules for a new row: use a free k in the set's table, **one row per k** (the last row written wins and can silently replace a stock knob); value 0 must keep classic behaviour (existing projects store 0 in slots stock has no row for); send-FX rows set `flags_set = 8` so they are never lockable; synth rows use free saved k values (FM Tone 34, 49; WaveTone 50-64; FM Drum 55-64; Swarmer 33-64); no randomiser; MIDI: no CC already in the set's map, none in 32-63, none taken by the CC parser (1, 2, 6, 64, 66, 94, 98, 99, 110, 120, 121, 123), NRPN 398 at most; Overbridge id outside stock's 0..387 (e.g. `0x400`+n, untested with the plugin). `[doc]` {dn2-cfw-param-table}
- **P-lock trap:** a row is lockable when display flag bits 0 and 3 are clear; locks are stored as (track, k), so an FX row with k 70 could create a lock on a sound's slot 70, which stock would play back. A bad row can write past map tables, replace a stock knob, or leave stray p-locks that persist after returning to stock. A project saved on a grown build and loaded on stock 1.12 is **untested on hardware**. `[doc]` {dn2-cfw-param-table}
- Checks used: brick checker 12/12 for GT00/GT01 ("a pass is not proof for code changes"), `scripts/t65_build.py check_rows` for FX rows, `pg_boot` only skips ids outside `0x141`-`0x17f` (it does not check k, flags, CCs or Overbridge ids), an emulator run of 7,100 MIDI messages giving the same 991 parameter sets as baseline. Never flash `param-test-dn2` or `fx-page2-dn2`. `[doc]` {dn2-cfw-param-table}

## Limits and budgets
- **USB upgrade limit 2 MiB**, not checked by the receiver; oversized images stall at the end, nothing written, power cycle clears. `[hw]` {dn2mk2-firmware-md} ([I3](../INCIDENTS.md#i3-usb-upgrade-receiver-does-not-check-the-2-mib-limit))
- **DSP image limit 1,048,575 bytes**; recent dn2mk2 builds sit at ~1,017,000-1,018,000. `[doc]` {dn2mk2-firmware-md}
- DSP time: SETTINGS > SYSTEM > DSP LOAD shows it; **at 100 % the audio crackles.** Heavy machines can push it over. `[hw]` {overtone}
- dn2mk2 cost figures: a PERC voice up to ~41,000 instructions per block, P-I machines ~9,000-19,000; Monomachine budget about two SIDs, four DPRO Waves, one DDRW and one DENS, or two VO-6 at once. A frame guard silences voices that no longer fit (limit 0.6 of the frame, estimated, not measured). `[doc]` {dn2mk2-firmware-md}
- Fast on-chip DSP memory vs DDR: voice state moved to fast memory in dn2mk2 v0.32; Monomachine tables and P-I delay lines remain in DDR. Savings can only be measured on a unit. `[doc]` {dn2mk2-firmware-md}
- Overtone: LOOP records 8 s stereo per track; LOOP in STRC mode, P-I and many SOPHIE voices can push DSP over 100 %. `[doc]` {overtone}

## Sample memory (dn2mk2)
- Pool of 400 MB (368 MB user samples + 32 MB recordings, ~5.5 min), up to 122 slots, RAM-checked at power-on (~0.7 s); +Drive library ~20 GB in a region the stock OS does not touch, up to 2,048 samples; slices up to 64 per sample, stored in a 128 KB area. Power-on load grows with stored samples (~30 s for 20 MB). **The 400 MB pool has never run on hardware** per FIRMWARE.md v0.22. `[emu]` {dn2mk2-firmware-md}
- **A stock DN2 has no sample filesystem, and a mod that mounts one must also create it** (armio R012, 2026-11-03). R012 mounted an existing sample filesystem but did not create one on a unit that never had it; on such a unit Transfer showed 0% Free / 0 bytes, uploads stalled and connections failed. The author says stock FORMAT +DRIVE, EMPTY RESET and FACTORY RESET do not create it and can erase projects. The bug was found by new users; the author's own unit had storage prepared during development, which is why owner testing missed it. A test on a freshly flashed stock unit is the only check that catches this. `[doc]` {armio-samples} ([I12](../INCIDENTS.md#i12-a-sample-machine-mod-could-not-create-the-storage-it-needed))
- **Stock eMMC TRIM can fail with TRIM ERROR on a busy card (OS 1.11).** A unit running dn2mk2 v0.39 stopped with TRIM ERROR at two different sector ranges while erasing mod data. dn2mk2's reading of the stock code: TRIM `0x4012c4b2` fails only when CMD35/36/38 get no answer (command timeout); after CMD38 the busy wait arms the DAT0 edge interrupt (`0x4012c53e`) **before** testing DAT0 (`0x4012c544`), so a short TRIM whose card finishes in between leaves a stale semaphore post (`0x4461b6c0`), the next TRIM on a really busy card returns at once, and the call after it gets no answer. The driver has no timeout. v0.40's fix: read the eSDHC present-state register `PRSSTAT` `0xfc0cc024` before every TRIM and verify read and call only when the card is idle; retry a failed call five times (TRIM is idempotent); report ERASE PAUSED and continue on request. The error is `[hw]`; the race is a static reading of stock code, not seen on the bus. Anything that issues TRIMs through the stock driver on a DN2 (and, not checked, a DT2 with the same driver) should do the same. `[hw]` {dn2mk2-v040} ([I1](../INCIDENTS.md#i1-stock-emmc-trim-fails-with-trim-error-on-a-busy-card))

## Sections
Protected: sections **2, 4, 5 and 8** (bootstrap, updater and others) must stay byte-identical to stock in dn2mk2's gate; mods change only **3 (MAIN OS) and 7 (DSP)**. Five stock machines; 16 track buffers. 1.10E rebuilt the bootstrap and moved its load address, 1.11 changed it again. `[doc]` {dn2mk2-safety}

## Recovery (full procedure in [`../common/flash-procedure.md`](../common/flash-procedure.md))
- FUNC at power-on -> TRIG 4 (OS UPGRADE) -> Elektron Transfer **LEGACY OS UPGRADE** over **5-pin DIN MIDI to MIDI IN; USB does not work in this mode**; takes ~12-15 min, do not interrupt. The bootstrap that holds this menu must stay byte-identical (the brick checker refuses changes). `[hw]` {overtone} {dn2mk2} {dn2-cfw}
- Overtone 1.0 broke the Transfer update path (stall at "Receiving"/"PREPARING..."); fixed in 1.0.1, way out = STARTUP menu over DIN. Details and the release test that catches it: [`../common/recovery.md`](../common/recovery.md). `[hw]` {overtone}
- Pre-flash safety kit: back up +Drive, keep the stock OS file for the exact version, volume down, DIN cable ready, check the file's SHA-256 against the gate record (`certutil -hashfile FILE SHA256` on Windows). `[doc]` {dn2mk2-firmware-md}
- The ~80% recovery-path stall once reported for dn2_firmware_explore's own images was the MIDI link: stock 1.10E stalled on the same route. Details: [`../common/recovery.md`](../common/recovery.md). `[hw]` {dn2-firmware-explore}

## dn2-cfw working set (README "Getting started")
Prerequisites: macOS on Apple silicon (Linux likely for most), Python 3, the user's own `Digitone_II_OS1_12.syx` in `elektron-firmware/`. Upstream tools are cloned into `vendor/` at the commits in `VENDOR.md`; digikit and elekloader come as the author's forks on branch `dn2-1.12` (digikit: 1.12 support, audio clock, DIN MIDI, LEDs, live play; elekloader: a Digitone II 1.12 profile and the `core-dn2` hook bus). Every candidate image must pass `tools/brickcheck` (12 checks) before it is flashed; compile C to SHARC code with selache/selcc and splice with `tools/dspsplice`; use elektron-firmware-tool for the `.syx` format and rebuild. The README does not give a flashing procedure (see `../common/flash-procedure.md`). `[doc]` {dn2-cfw}
Build ladder, all reported as run on the unit: EF01 (renamed stock: proves rebuild/seal/flash), FLG1 (flanger in place of chorus), FTD1 (+ one-head tape delay with loop filters, wow/flutter, wear, pitch bends on TIME), DH01 (core + MIDI test mod), FTN1 (screens renamed), GT00 (parameter table moved, +63 knob ids), GT01 (+17 hidden rows, 3-band compressor prerequisite). Not yet on the unit: the 3-band compressor and a Space-Echo-style delay. `[hw]` {dn2-cfw}
Notes in the repo mark each claim `[verified]` or `[inferred]` - copy that convention. `[doc]` {dn2-cfw}

## Stock intro (OS 1.11 and 1.12)
The intro works as on the Digitakt II: its own task at priority 7 above the main OS, scene tables, one current-entry pointer (1.12 `0x42c4cacc`, 1.11 `0x42c4bacc`).
